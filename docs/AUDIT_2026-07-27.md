# Hallow Total Audit — 2026-07-27

## Executive verdict

Hallow is a real local agent runtime, not only a landing page. Its strongest foundations are the local state boundary, explicit agent/skill manifests, model routing, MCP, approval policy, traces, readiness evidence, and repair loops. The largest product weakness was the path from “repository” to “running daily service”: installation depended on a developer toolchain, process lifecycle was incomplete, and the polished terminal did not extend to installation failures.

This audit rebuilds that path around four public commands:

```text
hallow              operator terminal
hallow open         start if needed and open desktop
hallow status       runtime + process + doctor state
hallow stop         stop the managed runtime
```

## Official benchmark

The comparison was made against the current first-party repositories and documentation for:

- NousResearch Hermes Agent: one-line installers, dependency bootstrapping, `setup`, `doctor`, update flow, and direct terminal entry.
- OpenClaw: one-line installers, onboarding, verification, managed gateway startup, doctor, and explicit installer flags.

The useful lesson is not to copy their branding. It is to make installation an owned product surface with predictable stages, recovery information, and a healthy process at the end.

## Findings and changes

| Severity | Finding | Change in this audit |
| --- | --- | --- |
| P0 | `hallow start` blocked the terminal, while background start only existed inside the operator shell. | `hallow start` now launches a managed background runtime; `--foreground` preserves the debug/server mode. |
| P0 | No public top-level `open` or `stop` lifecycle existed. | Added `hallow open`, `hallow stop`, service state, PID, log paths, readiness wait, and stale-record cleanup. |
| P0 | Runtime detection accepted any Hallow health response on the port, even if it belonged to another home. | Health ownership now verifies the resolved runtime home before managing the process. |
| P1 | Public install required Git, Corepack, pnpm, Node 22, a full dependency install, and a local build. | Git and Corepack are removed from the public requirement. Installers download a staged source archive, provision pnpm, build, verify, and promote only after success. |
| P1 | A dependency installed by `winget` could remain invisible in the same PowerShell process. | Windows installer refreshes machine/user PATH after dependency provisioning. |
| P1 | Windows and Unix installer behavior diverged. | Both now expose dry-run/verify/no-start/no-open modes, staged upgrades, logs, launchers, lifecycle start, update, and uninstall. |
| P1 | Installed launchers forced Windows into a non-interactive `terminal` snapshot and exited. | Launchers now pass through an empty command so `hallow` opens the actual operator shell on a TTY. |
| P1 | Generated desktop launchers still depended on `corepack pnpm`. | Generated launchers now invoke the built CLI directly with Node. |
| P1 | Installer output hid neither noisy builds nor the useful failure tail. | Build output is captured in a timestamped log; only the final failure tail and actionable log path are shown. |
| P2 | Updating could modify the active checkout before a build was proven. | Remote installs build under a staging path, retain `source.previous`, and promote the new source only after build verification. |
| P2 | `scripts/install.*` and `site/install.*` could silently drift. | Added `pnpm installer:check` to enforce byte-identical public copies and contract markers. |
| P2 | Documentation described manual pull/rebuild/uninstall steps. | README and web docs now document `start/open/status/stop/update/uninstall` and installer inspection modes. |

## Architecture weaknesses still open

1. **No signed prebuilt release artifact.** Public installation still performs a source build. A release pipeline should publish platform-neutral bundled CLI artifacts plus checksums/signatures so normal install does not download a development workspace.
2. **No native OS service manager.** The managed detached process is usable, but it is not yet a Windows Scheduled Task, macOS LaunchAgent, or Linux systemd user service. It will not automatically recover after reboot.
3. **Monolithic implementation.** `packages/cli/src/index.ts` and especially `packages/runtime/src/index.ts` contain too many unrelated responsibilities. Commands, service lifecycle, HTTP routes, installer metadata, and UI rendering need module boundaries.
4. **Insufficient automated tests.** Typecheck/build and live smoke tests exist, but lifecycle, installer upgrade/rollback, API authorization, and Windows quoting need committed unit/integration coverage.
5. **Static release metadata.** CLI version and release label are hard-coded. Build provenance should be generated from package version, commit SHA, and release channel.
6. **Single service record.** One Hallow home currently manages one recorded runtime. Multi-profile or multiple-port operation needs a service registry keyed by profile/port.
7. **Installer provenance.** Unix locally provisioned Node is SHA-256 verified against Node’s published manifest, but Hallow source archives do not yet have a project-owned signed checksum manifest.
8. **First-run provider onboarding.** Setup creates a fully inspectable local runtime, but provider credentials and a recommended model route still require follow-up configuration. A short interactive onboarding wizard remains necessary.

## Recommended next release gates

### 001.1 — installation confidence

- Publish a versioned release archive and SHA-256/Sigstore manifest.
- Test clean install and upgrade in GitHub Actions on Windows, macOS, Ubuntu, and WSL.
- Add installer rollback on setup/doctor failure after source promotion.
- Generate version/commit provenance at build time.

### 001.2 — daily operation

- Add `hallow service install|remove|restart|logs` using native OS service managers.
- Add a provider onboarding wizard with safe secret storage and route test.
- Open the desktop to a first-run checklist instead of a general runtime dashboard.

### 002 — maintainability

- Split CLI commands by domain.
- Split runtime HTTP, memory, gateway, marketplace, browser, and autonomy services.
- Add contract tests for every state-changing HTTP route and approval boundary.

## Verification contract

```bash
pnpm installer:check
pnpm typecheck
pnpm build
hallow setup
hallow doctor
hallow start
hallow status --strict
hallow open --print
hallow stop
```

The installer-specific dry runs are:

```powershell
.\scripts\install.ps1 -DryRun -NoStart -NoOpen
```

```bash
bash scripts/install.sh --dry-run --no-start --no-open
```
